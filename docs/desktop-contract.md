# Desktop interface contract

The 1.1 desktop app targets Windows and has a minimum window size of 800x560. The terminal interface remains
available through the Python package and repository on Windows, Linux and macOS. Both interfaces use the same
providers, collector, session model, views and persisted preferences. Their run tables share columns, content
and sorting, with horizontal scrolling when needed. Both use a default order of pending questions, live
sessions and newest starts; Details retains the full technical inspection.

## Runtime and distribution

The desktop presentation uses local HTML/CSS/JavaScript in pywebview, rather than a served Textual terminal. The Python entry starts the session reader, creates a narrow JavaScript bridge and loads packaged local content. Prefer inline packaged assets to avoid exposing a public local application server. Do not render session content as trusted HTML or permit remote navigation in the privileged window.

Ship one public Windows app entry, `bitacora.exe`. The terminal command remains `bitacora` or `python -m bitacora`; a second public CLI executable is not part of this release. Keep GUI imports lazy so terminal usage and informational flags work without window dependencies.

## Bridge methods

All calls return JSON-compatible values. All strings presented to users come from the existing English/Spanish translation table. Run keys are identifiers supplied by the service, never filesystem paths or shell commands supplied by the frontend.

- `bootstrap()` returns `{version, lang, strings, preferences, views, themes, first_run, live_only}`. `strings` maps translation keys to strings in the selected language, with named placeholders formatted by the frontend. `preferences` contains `view`, `lang`, `hours` (capped at 72), `notify`, `theme`, `font_size` and `list_height`. Views contain `id` and `name`; themes contain `id`, `name` and `colors` with `background`, `foreground`, `panel`, `muted`, `accent`, `primary`, `secondary`, `success`, `warning` and `error` hex strings. `first_run` asks the interface to show the existing initial view/settings choice. `live_only` applies the launch flag without altering saved view preferences. A theme that is not offered, or none saved, is shown as `monokai` (the default theme, `themes.DEFAULT_THEME`).
- `get_snapshot(sort_key=None, sort_direction=None)` returns `{revision, reader, runs, quotas, counts, notices}`. With no sort arguments it uses the shared default order: pending questions, live sessions and newest starts, with run key breaking ties. Sorting accepts a desktop column key (`status`, `agent`, `name`, `model`, `repo`, `now`, `last`, `dur`, `ctx`, `tok`, `cmds`, `files`, `mode` or `pid`) and direction `asc` or `desc`; `ctx` sorts by context use and `tok` by the cumulative Total. `reader` contains `state`, `error` and `age`; state is `loading`, `ready`, `stale` or `error`. Runs contain `key`, `provider`, `agent` (short provider plus localized short origin kind), `agent_full` (full provider plus localized full origin kind), `origin_kind`, `origin_raw`, `label`, `status`, `status_source`, `live`, `alive`, `repo`, `cwd`, `model`, `effort`, `effort_source`, `access_kind`, `access_raw` (also exposed as raw `sandbox`), `start_ts`, `started_text`, `duration`, `last_ts`, `tokens`, `usage_basis`, `tokens_text`, `context_tokens`, `context_text`, `context_window` (also exposed as `ctx_window`), `context_window_assumed`, `n_cmds`, `n_fail`, `n_files`, `pid`, `activity` and `actions`. `status_source` is `process` or `transcript` when status is `running`, and null otherwise; Details shows the localized source. `tokens_text` and `context_text` use the terminal formatter to preserve identical rounding. Ctx is a percentage only when its model window is known; otherwise it is the context token count. Total is cumulative, labeled Processed for Claude Code and Reported for Codex, with its basis explained in Details. `started_text` is local start time formatted as `DD/MM HH:MM`, or `-` when unknown. The front end keys each rendered row by the run's `key`, not its current position. `actions` contains booleans `open_result`, `open_log`, `copy_resume` and `stop`. Counts include `total`, `live`, all ten normalized statuses (`asking`, `running`, `starting`, `your_turn`, `done`, `failed`, `limited`, `stopped`, `quiet`, `unknown`) and `views` mapping each view id to `{total, live}`. Quotas use `{reporting, windows, limit}` for both providers. Windows include `id`, display `name`, `minutes`, `scope`, `used_percent`, `resets_at`, `as_of` and `source`; limits include their normalized window/name, scope, hit time, reset time/text and source. Expired windows display as reset with no percentage or past renewal time; unknown percentages show as `?`. Notices are `{kind, text}` objects for transitions in the current view: entering `asking` notifies from any prior status; a prior `running`, `asking` or `starting` status followed by `done` or `your_turn` notifies as complete, and followed by `failed`, `limited` or `stopped` notifies as stopped. Notifications respect the preference.
- `get_detail(key)` returns `{run, events, messages, files, log, result, resume, info}` or `{error}` for a missing run. Events are `{seq, ts, kind, text, detail, dur, ok, code, sub, plus, minus, count}`. Messages are `{ts, text}` objects. Files are `{path, kind, count, ts, plus, minus}` objects. `log` and `result` contain `path`, `text` and `available`; missing result files fall back to the last agent message. `resume` is a command string or null; `info` is a list of `{label, value}` objects including status source when it is available. Reading is bounded and failures remain visible.
- `save_preferences(patch)` validates only the documented preference keys, persists supported values and returns a new bootstrap object. Language, theme, view, history window and notifications retain their existing meanings. Font size is a desktop presentation preference. `list_height` is a finite number (booleans rejected) from 0.15 through 0.85, the list's fraction of the flexible list/pane area. An unsaved or invalid saved value is returned as null and selects automatic sizing: about half the flexible area, with at least four rows at 800x560 with 18 px text and more when space permits. Null patches are rejected; saving other settings preserves automatic sizing. Invalid patches are rejected before any values are persisted. Changes must not corrupt legacy session migration or window placement. Each save and each bootstrap first adopts what another interface (the terminal app or a second window) saved since this one last read the preferences; a save writes only the keys in the patch, so a setting the caller did not change is never written back stale.
- `open_result(key)` and `open_log(key)` open only the service-known path for that run in the system application. They return `{ok, message}`. They do not accept arbitrary paths.
- `copy_resume(key)` returns `{ok, text, message}` containing the provider's existing resume command. The frontend copies that exact text or presents it for manual copying. It must not claim to reopen or answer a session automatically.
- `request_stop(key)` returns `{ok, token, message, pid}`. A successful request issues a short-lived confirmation token tied to the selected run and process creation time. The default confirmation choice is cancel.
- `confirm_stop(token)` validates the token and process identity again before terminating the selected agent tree. Tokens are single-use. PID reuse, vanished processes and invalid/stale tokens fail safely. The frontend cannot bypass confirmation by supplying a PID.
- `get_scene(columns)` returns `{columns, rows, palette, cells}` for the existing lighthouse/sky/code scene. Each row is a list of runs `[text, fg, bg, bold]`, one per stretch of equal style, with `fg` and `bg` indexing `palette` (hex colors); half-block cells can be drawn as two colored rectangles. This preserves the existing visual identity without duplicating the scene algorithm. Animate only while the home/settings scene is visible; avoid overlapping calls.
- `quit()` asks the application window to close. `toggle_fullscreen()` toggles the actual window. Closing the window stops and joins the reader. If WebView2 still holds its private profile open, an internal helper validates its owner marker, waits for this process to exit, and removes only that profile. The release smoke stays pending until that cleanup is verified.

Bridge methods validate identifiers, types, ranges and permissions in Python. Session content is untrusted data. Confirmation and process identity checks belong to the service even when the interface displays a dialog.

## Presentation and behavior

Preserve the project's lighthouse, falling code, time-aware sky, restrained technical palette and theme support. Improve readability and discoverability within that direction. The interface is a local desktop monitor, without marketing content or infrastructure terminology in its normal flow.

The monitor prioritizes questions and actionable state. Keep the selected session stable across refreshes. Preserve Activity, Messages, Files, Log, Result and Details. Both run tables use Status, Agent, Name, Model, Folder, Now, Last activity, Duration, Ctx, Total, Cmds, Files, Mode and PID, in that order. Agent uses lowercase `codex`/`claude` plus a short localized origin kind; the hero and Details retain full names; raw origin stays in Details. Model includes effort. Name and Now end with ellipses at their 60 and 40 character caps and retain full text in desktop tooltips and terminal summary/Details. Status and Name stay sticky on the left of the desktop table during horizontal scrolling, and the scrollbar remains visible. The desktop header stays fixed during vertical scrolling; the terminal DataTable scrolls horizontally. Retain the full technical inspection in Details, including `status_source` when running. Preserve verbose detail, live-only filtering and auto-scroll, with visible state and usable keyboard shortcuts. Do not replace the selected detail DOM on every refresh when nothing changed, or reset its scroll position while auto-scroll is paused.

The run table sorts by a heading in ascending order, descending order, then its shared default order on repeated activation. The default puts questions first, then live sessions, then the newest starts; stable ties use the run key. Missing values remain last in both directions. Numeric counts, PIDs, durations, context percentages and timestamps sort by their numeric values; text uses case-folded code-point order. Only the active heading shows an arrow. Desktop headings are keyboard-focusable buttons with an announced sort direction; the third activation resets sorting. In both interfaces `<` and `>` step through columns, and Ctrl+R resets sorting. In the terminal, Ctrl+P offers each column and reset. Desktop `r` and `F5`, and terminal `r`, refresh the snapshot.

The adaptive header has a first line for brand, counts, view/window, reader health and Live; desktop adds Home and Help. Quotas stay on one compact line with bars, percentages and shortened renewal times, with full renewal details in desktop tooltips and Details. A question line appears only when questions are open, and its asking count moves into the first line only when the question line is hidden. Counts compact to symbols before non-urgent counts disappear; asking/running counts and view/window remain. Reader health shortens to a dot with a tooltip. The terminal may hide the quota line by itself on very short screens.

In both interfaces, `g` toggles a maximized list, hiding the selected-run section, tabs and panes until restored. The footer and help show this shortcut and its state. Footer groups refit after text-size or preference changes, never overflow, and keep the compact maximize-state and Help keys at short heights. In both interfaces, `m` toggles Plain text in Messages and Result. A horizontal drag handle between the desktop list and selected-run section resizes the list and saves `list_height`; maximizing temporarily overrides the height without changing the saved fraction.

The selected-run hero sits directly above the detail tabs in both interfaces. At normal heights, its four rows show status/name/agent/folder; model, effort, access, start time, duration and last activity; cumulative Total, context, commands/failures and files; then Now. A pending question follows. At short heights it compacts to two rows: status, name, agent, folder and actions; then Now or the question. The rest of the technical values stay in Details. Desktop uses a padded rounded panel with actions on its first row; the terminal uses a bordered panel with a neutral title. Pending questions wrap up to three lines in the terminal. Stop stays visible; Result, Log and Copy resume move into a keyboard-accessible overflow menu when needed. Long labels and metric values ellipsize without cutting labels. Maximizing the list hides the hero with the detail area.

The terminal global header has the adaptive brand/counts/view/window line with reader health and Live aligned right, a quota line, and an optional question chip line. There is no fold toggle. One continuous thin rule follows. It is still and muted while nothing runs; while sessions run a soft beam of light sweeps along it left to right, about 3 s a pass, in the accent colour, or in the theme warning colour while a session waits for an answer. Reduced motion keeps the still rule. Header chips and footer click targets never underline text or spaces.

Home/settings retains view counts, language, history window, notifications and theme. The first-run choice and saved configuration retain their existing precedence. The source of truth for translated labels is Python, including errors, empty states, status, confirmation and help. User content and provider/model names are data and remain verbatim.

Use local fonts with a deliberate Windows fallback; code, logs and diffs remain monospaced. No font, image, script, telemetry or other asset is fetched from an external service. A browser preview, if used during development, runs on synthetic fixtures and has no access to privileged actions or real sessions.

## Acceptance

- Synthetic sessions show the expected sixteen runs, quotas, questions, result, log, messages and file changes in both languages.
- A user can identify the pending question, select it and find the next action using the mouse without learning the footer first.
- Selected row, tab, verbosity, filters and paused scroll survive refreshes. Keyboard navigation and copying remain available.
- All controls and dialogs work at the minimum window size, and text remains usable with Windows display scaling at 100%, 125% and 150%.
- Reader failure or stale state is visible; incomplete or unknown data is not represented as healthy zero usage.
- Agent-supplied markup cannot execute scripts, navigate the privileged window or invoke bridge actions. Arbitrary paths, PIDs and confirmation tokens are rejected.
- A frozen Windows demo starts without a console or sibling CLI executable, displays live synthetic updates, and closes its reader cleanly. CLI demo and informational flags work with no GUI dependencies installed.
- The existing terminal suite and meaningful desktop/service tests pass. Documentation and captured examples use synthetic data and LF files only.
